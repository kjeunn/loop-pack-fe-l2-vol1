# 9주차 E2E 범위 설계

E2E는 통합 테스트보다 비싸고 UI가 바뀔 때마다 고칠 곳이 생긴다. 그래서 개수를 늘리지 않고, 붙일 곳과 안 붙일 곳을 근거로 정한다. 이 문서는 그 근거를 세우고, 4단계에서 만들 테스트와 만들지 않을 것을 확정한다.

시드 집계 방법과 결정은 작성자가 정했고, 근거 수치는 `fixtures/events-30d.jsonl`(30일·8,000세션·22,427이벤트)을 집계해 뒷받침했다.

## A. 이벤트 스키마

2단계에서 확정한 계측 스키마다. 새 결정은 없고, 코드(`src/analytics/schema.ts`·`session.ts`)에 있는 것을 옮겨 적는다.

### 이벤트 이름

시드 스키마를 그대로 채택한다. 우리 앱에 없는 화면의 이벤트만 뺀다.

| 이벤트                                               | 계측 지점               |
| ---------------------------------------------------- | ----------------------- |
| `product_list_view`                                  | 목록이 실제로 그려진 뒤 |
| `category_filter_change`·`sort_change`·`page_change` | 목록 조작               |
| `cart_add`                                           | 담기                    |
| `wishlist_add`                                       | 찜                      |
| `login_start`·`login_success`·`login_fail`           | 로그인 시작·성공·실패   |
| `order_start`·`order_complete`                       | 주문 시작·완료          |

**제외** — `product_detail_view`는 시드 앱엔 상품 상세 화면이 있으나 우리 앱엔 목록만 있어 찍을 화면이 없다. `client_error`는 오류 이벤트이고, 뒤([노이즈 기준](#노이즈-기준))에서 보듯 전량이 그 상세 화면의 이미지 오류라 우리 경로에 붙지 않는다.

### 공통 프로퍼티

모든 이벤트에 `setCommonProperties()`로 붙는다. 값은 발생 시점에 평가된다.

| 프로퍼티    | 값                                                                                                                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessionId` | `sessionStorage` + `crypto.randomUUID()`. 저장소 접근이 막히면 페이지 동안만 유지되는 메모리 값, `randomUUID`가 없는 비보안 컨텍스트면 대체 생성. 브라우저 세션 식별자로, 인증 세션과 별개다 |
| `device`    | `matchMedia`로 `mobile`·`tablet`·`desktop` 판별                                                                                                                                              |
| `ts`        | 발생 시점 ISO 8601                                                                                                                                                                           |
| `userId`    | 로그인 상태일 때만. `AnalyticsSessionSync`가 세션 상태를 관측해 넣는다                                                                                                                       |

시드의 공통 필드(`sessionId`·`ts`·`device` 전량, `userId`는 로그인 후)와 일치한다. `login_success`는 세션 반영(`AnalyticsSessionSync`)보다 먼저 찍히므로 `LoginForm`이 로그인 응답의 `user.id`로 먼저 식별한 뒤 찍는다 — 시드의 `login_success`는 586건 전부 `userId`를 갖고 `login_start`는 0건인데, 그 경계와 같다.

### 시드 매핑

이름은 시드와 전부 일치해 이름 매핑표가 필요 없다. 프로퍼티만 우리 데이터에 맞춰 조정한다.

| 이벤트                         | 시드 프로퍼티             | 우리 프로퍼티          | 근거                                                                                             |
| ------------------------------ | ------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------ |
| `cart_add`                     | `{ productId, quantity }` | `{ productId }`        | 우리 장바구니엔 수량 개념이 없어 항상 1이다. "몇 개 담나"에 답할 데이터가 없어 `quantity`를 뺀다 |
| `order_start`·`order_complete` | `{ productId }`(단수)     | `{ productIds }`(복수) | 시드는 단일 상품 주문 모델이고 우리는 여러 상품(장바구니) 주문이라 배열로 매핑한다               |
| `order_complete`               | `totalPrice` 포함         | 제외                   | 결제·쿠폰·배송 개념이 없어 실제 결제액에 답할 값이 없다                                          |

나머지 이벤트(목록 조작·로그인·찜)의 프로퍼티는 시드와 모양이 같아 변환할 매핑이 없다.

## B. 시드 로그 분석

### 집계 방법

| 축        | 결정                                                                                                                                      | 근거                                                                                                                                                                                                 |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 경로 단위 | 화면 묶음. 목록 조작(진입·필터·정렬·페이지)을 "목록" 한 경로로 접고, 담기·찜은 전환 행동이라 분리, 주문 시작·완료는 이탈 측정을 위해 분리 | E2E는 이벤트가 아니라 화면 흐름을 타므로 분석 단위를 화면에 맞춘다. 조작을 이벤트별로 두면 목록 조작이 순위 상단을 차지해 전환·퍼널 단계를 가린다                                                    |
| 비율 분모 | 절대 도달률. 노이즈를 걸러낸 전체 세션(7,514)을 모든 행의 분모로 통일                                                                     | 순위는 비교 가능한 단위라야 성립한다. 행마다 분모가 다르면(도달률 vs 퍼널 전환율) 줄을 세울 수 없다. 퍼널 전환은 이탈률 칸이 담는다                                                                  |
| 이탈률    | "다음 단계 미진입" 정의. 값 옆에 이탈 방식(즉시 이탈 vs 측면 이동)을 주석으로 붙인다                                                      | "세션 마지막" 정의는 경로와 성공 사이에 중간 이벤트(`login_fail` 등)가 끼면 이탈을 과소계상한다. 로그인이 그 예로, "세션 마지막" 정의로는 0%지만 실제 9%가 성공 못 하고 떠난다                       |
| 실패 비용 | 우리 아키텍처의 실패 모드(세션 만료 401·가드·주문 API) × 시드에서 얻는 도달·이탈 규모. 시드 실패 이벤트가 아니다                          | 시드는 다른 앱의 로그라 우리 경로가 고장 났다는 기록을 남기지 않는다. `client_error`는 없는 화면 오류이고 `login_fail`은 정상 거부(틀린 비밀번호)라 고장이 아니다. 우리 실패 모드는 우리 코드에 있다 |

### 노이즈 기준

시드에는 진짜 사용자 행동이 아닌 이벤트가 섞여 있고 표시는 없다. 무엇을 노이즈로 보고 걸렀는지는 아래와 같다. 세 종류를 각각 다른 방식으로 걸렀다.

| 종류 | 무엇                                                                                  | 규모          | 제외 방식                      |
| ---- | ------------------------------------------------------------------------------------- | ------------- | ------------------------------ |
| 봇   | `device`가 `null`. 전량 단발 `product_list_view`이고 발생 시각이 100% 01시 UTC에 몰림 | 486세션(6.1%) | 세션 통째로 분모에서 제외      |
| 중복 | `sessionId`·`name`·`props`·`ts`가 완전히 같은 재전송                                  | 77줄(0.34%)   | 복사본만 제외, 세션은 유지     |
| 오류 | `client_error`. 전량 `IMAGE_LOAD_FAILED`이고 직전 이벤트가 100% `product_detail_view` | 103건         | 경로 집계 대상 아님(없는 화면) |

봇 판정의 근거는 `device`=`null` 세션이 매일 01시 UTC에만 몰린다는 점이다. 24시간 고르게 퍼지는 실트래픽과 구분된다. 부피형(이벤트 폭주)이나 규칙적 간격으로는 잡히지 않았다(세션당 최대 11이벤트, 균일 간격 세션 0). 중복은 클라이언트가 같은 비콘을 두 번 보낸 것이고, 오류는 우리 앱에 없는 화면의 오류라 애초에 우리 경로에 붙지 않는다.

### 거르기 전후 순위

노이즈를 걸러도 경로 순위는 바뀌지 않는다. 봇 486세션을 빼 분모가 8,000 → 7,514로 줄면서 비목록 경로 비율이 약 1%p 오르지만, 순서는 그대로다.

| 경로      | Before 세션 | Before 비율 | After 세션 | After 비율 |
| --------- | ----------- | ----------- | ---------- | ---------- |
| 목록      | 8,000       | 100.0%      | 7,514      | 100.0%     |
| 담기      | 1,309       | 16.4%       | 1,309      | 17.4%      |
| 로그인    | 644         | 8.1%        | 644        | 8.6%       |
| 찜        | 480         | 6.0%        | 480        | 6.4%       |
| 주문 시작 | 419         | 5.2%        | 419        | 5.6%       |
| 주문 완료 | 277         | 3.5%        | 277        | 3.7%       |

순위는 두 경우 모두 목록 > 담기 > 로그인 > 찜 > 주문 시작 > 주문 완료다. 노이즈 총량이 작아(중복 0.34% + 봇 6.1%) 분모를 무엇으로 잡든 순위가 흔들리지 않는다는 것이 결과다.

### 경로 분석표

| 경로      | 세션수 | 비율   | 이탈률(다음 단계 미진입)                           | 실패 비용                                    | E2E 가설   |
| --------- | ------ | ------ | -------------------------------------------------- | -------------------------------------------- | ---------- |
| 목록      | 7,514  | 100.0% | 82.6% — 대부분 더 둘러봄(측면), 스토어의 정상 이탈 | 클라이언트·무인증. 막히면 진입점이 막힘      | 안 붙임    |
| 담기      | 1,309  | 17.4%  | 68.0% — 상당수 로그인하러 감(측면)                 | 클라이언트. 막히면 담기 불가                 | 안 붙임    |
| 로그인    | 644    | 8.6%   | 9.0% — 전량 자격 오류 이탈(즉시 이탈 아님)         | 만료 401·가드. 막히면 주문서·주문내역이 막힘 | 붙임(인증) |
| 찜        | 480    | 6.4%   | N/A — 퍼널 밖 side action                          | 클라이언트. 막히면 찜 불가                   | 안 붙임    |
| 주문 시작 | 419    | 5.6%   | 33.9% — 순수 이탈(측면 이동 0)                     | 가드·세션. 막히면 구매 진입 불가             | 붙임       |
| 주문 완료 | 277    | 3.7%   | N/A — 종료 단계                                    | 주문 API·세션. 막히면 매출                   | 붙임       |

이탈 방식은 경로마다 다르다. 주문 시작은 즉시 이탈과 다음 단계 미진입이 같은 33.9%로, 주문서를 버리면 다른 데로 가지 않고 그냥 떠난다. 로그인은 즉시 이탈 0%인데 미진입 9%로, 떠난 9%가 전부 `login_fail`을 받고 이탈했다. 담기의 미진입 68% 중 상당수는 진짜 이탈이 아니라 로그인을 거치는 중이다(담기 뒤 `login_start`·`login_success`·`login_fail`이 뒤따른다). 숨은 퍼널은 목록 → 담기 → 로그인 → 주문 시작 → 주문 완료다.

마지막 칸은 가설이고, 최종 판단은 [C절](#c-붙일-곳과-안-붙일-곳)에서 한다.

## C. 붙일 곳과 안 붙일 곳

E2E 시나리오는 인증 플로우 1개와 인증 외 2개, 합쳐 3개다.

### 인증 플로우 (필수) — 빈도가 낮은데 붙인 경로

인증은 세션 도달 하위권(3.7~8.6%)이라 빈도 순위만 보면 E2E 후보가 아니다. 그러나 실패 비용이 최상위다. 로그인이 막히면 그 뒤 보호 경로(주문서·주문내역)가, 주문이 막히면 매출이 끊긴다. 게다가 미들웨어 리다이렉트·쿠키·SSR 로그인 상태의 얽힘은 통합 테스트가 잡지 못해 유일하게 미검증이다. `src/proxy.ts`에는 (이 시점엔) 테스트가 없었고 — 리팩토링에서 판정 유닛(유효·없음·만료·위조·비객체 페이로드)을 넣었지만 "어느 경로에 거나"(`matcher`)는 여전히 E2E만 본다 — 로그인·주문 컴포넌트 테스트는 라우터를, SSR 로그인 상태 테스트(`layout`)는 쿠키를 목킹한다. 빈도와 실패 비용의 역전이 로그(빈도)만 보고 정하면 안 되는 이유다.

4단계에서 세 갈래를 다룬다.

- 미로그인으로 보호 경로 진입 → 로그인 → 원래 경로 복원
- 세션 만료 경계 — `expired` 시나리오로 재현(리팩토링에서 실제 만료 쿠키 E2E를 더함, [§F](#f-리팩토링--초록불-아래에서-찾은-것))
- 잘못된 자격 증명 — `invalid` 시나리오 또는 틀린 비밀번호

### 인증 외 2개

**A. 장바구니에서 주문으로 이어지는 흐름 (담기 → `/cart` → 주문서 → 완료 → 내역)**

순수 신규 가치는 담은 상품이 실제 주문 요청으로 넘어가는지 확인하는 데 있다. 장바구니에 담은 것이 주문 요청 본문으로 넘어가 내역에 반영되는지는 어느 테스트도 덮지 않는다(장바구니 E2E는 담기 지속만, 주문 API 유닛은 API만 검증한다). `/cart`는 `/order-form`으로 가는 유일한 관문("주문서로 이동" 링크)이고 `CartList`엔 별도 테스트가 없어, 이 시나리오가 그 화면을 검증하는 유일한 테스트가 된다. 로그인은 `storageState`로 재사용해 이 시나리오에서 로그인 폼을 다시 타지 않는다.

**B. 주문 실패 시 장바구니 유지**

`error` 시나리오로 주문을 실패시켜, 장바구니를 비우지 않고 재시도할 수 있는지 검증한다. 데이터 손실 방지이고, 5단계(실패를 일부러 내서 E2E가 잡는지 확인)의 철학과 맞는다.

### 빈도가 높은데 안 붙인 경로

목록·담기·찜·홈과 상태 지속(새로고침 복원)은 붙이지 않는다. 무인증·클라이언트 상태라 E2E가 유일하게 잡는 미들웨어·쿠키·SSR 얽힘이 없고, 8주차 E2E와 통합 테스트가 실제 흐름을 이미 덮어 추가 E2E의 순수 신규 가치가 0이다.

- **목록**(도달 100%, 최고 빈도) — `products.spec.ts`가 뒤로·앞으로 가기 조건 복원을 실브라우저로 검증한다. 정렬·페이지 결과는 E2E가 아니라 통합(`ProductListView`)이 덮지만, 순수 클라이언트 URL 상태 → 결과라 통합으로 충분하다.
- **담기**(17.4%) — `products.spec.ts`·`home.spec.ts`가 담기 지속을 검증한다. 이 경로는 시나리오 A의 셋업 단계로 등장한다.
- **찜**(6.4%) — `home.spec.ts`가 하트 토글을 검증한다.
- **홈** — 시드에는 홈 이벤트가 없어 빈도는 측정값이 아니라 랜딩=고트래픽 가정이다. `home.spec.ts`가 렌더와 prefetch를 이미 덮는다.
- **상태 지속** — 경로가 아니라 여러 화면에 걸친 동작이다. `products.spec.ts`("새로고침해도 담은 상품 복원")와 `cartStore` 통합이 덮는다.

`/cart`는 이 목록에 넣지 않는다. 시나리오 A가 지나며 덮기 때문이다. 로그아웃은 저빈도이고 단순(세션 제거·리다이렉트)이라 통합(`LogoutButton.test`)으로 충분해, "빈도 높은데 안 붙임"과는 다른 범주로 뺀다.

### 유지보수 비용 추정 — 시나리오 A

시나리오 A는 4화면(목록·`/cart`·주문서·내역)을 지나 셋 중 유지비용이 가장 크다. 화면의 무엇이 바뀌면 테스트의 어디를 고치는지 셀렉터로 셌다.

**문구가 바뀌면 — 6곳**

| 바뀌는 문구     | 고칠 곳 | 어디서 쓰나                                                                                                           |
| --------------- | ------- | --------------------------------------------------------------------------------------------------------------------- |
| "장바구니"      | 3       | 담기 `aria-label` · 담은 뒤 헤더 링크 · 완료 후 "장바구니 0". 한 단어가 세 곳에 퍼진 **유일한 핫스팟**                |

## D. 자가검증 실험 (5단계)

E2E는 비싸니 정말 값을 하는지 확인한다 — 인증 코드를 한 군데씩 일부러 고장 내고, 그때 E2E가 실패로 잡아내는지 본다. 잡으면 그 테스트가 진짜 검증을 하고 있다는 뜻이고, 못 잡으면 그 테스트는 헛돈 셈이다. 실험은 매번 같은 순서로 했다 — ① 전부 통과인지 확인 → ② 코드 한 곳만 고장 → ③ 표적 테스트를 돌려 실패를 확인 → ④ 원래대로 되돌림 → ⑤ `git diff`가 비었는지(원상복구) 확인. 통합 테스트(vitest)로도 잡히는지는 같은 고장을 vitest에도 걸어 직접 돌려봤다. 실험하는 동안 테스트 코드는 손대지 않았다.

| #   | 망가뜨린 곳                           | 어떻게 바꿨나                                                             | 결과 | 실패한 테스트                                  | 실패 메시지로 원인을 알 수 있었나                                                                                          | 통합도 잡나                                                                                                                                  |
| --- | ------------------------------------- | ------------------------------------------------------------------------- | ---- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `proxy.ts` 가드 적용 범위 (`matcher`) | `["/order-form","/orders"]` → `["/order-form"]` (`/orders` 제거)          | 잡힘 | auth.spec 복원 — 미로그인 진입 리다이렉트 단언 | 예. `toHaveURL(/login?redirect=%2Forders)`가 `/orders`를 14회 받아 실패 — 미로그인 `/orders`가 안 튕기고 잔류함이 드러난다 | E2E만 잡음 — 유닛 테스트는 `proxy` 함수만 직접 부르고 "어느 경로에 거나"(`matcher`)는 안 거친다                                              |
| 2   | `queryClient.ts` 만료 리다이렉트      | `location.assign(...)` 한 줄 제거                                         | 잡힘 | session-expiry — 만료 시 로그인 유도 단언      | 예. E2E는 `/login?redirect`가 안 와 실패, 통합은 `assign` 호출 0회로 실패                                                  | 실측 잡힘 — `queryClient.expiry.test.tsx` 실패 (`assign` 0회)                                                                                |
| 3   | `LoginForm.tsx` 복원 경로             | `safeRedirect(redirect)` → `safeRedirect(null)` (redirect 무시, 항상 `/`) | 잡힘 | auth.spec 복원 — 로그인 후 복귀 단언           | 예. 로그인 후 `/`로 가 `toHaveURL(/orders)` 실패, 통합은 `replace`가 `/orders` 아닌 `/`로 불려 실패                        | 실측 잡힘 — `LoginForm.test.tsx` 실패 (`replace("/orders")` 기대, `/` 받음). 리팩토링 후 복원은 hard navigation이라 단언은 `location.assign` |

**셋 다 잡혔고, 살아남은 고장은 없다.** (→ 이 결론은 _고른 세 건에 한해_ 참이었다. 리뷰 뒤 더 넓게 부수자 초록불 아래 결함이 넷 나왔다 — [§F](#f-리팩토링--초록불-아래에서-찾은-것).) 세 고장 모두 노린 그 지점에서 깔끔하게 실패했다 — 엉뚱한 데서 먼저 멈추거나(크래시) 오래 기다리다 실패(타임아웃)한 게 아니라, "이 URL이어야 한다"는 확인이 정확히 어긋나 실패했다. 그래서 실패 메시지만 봐도 원인을 알 수 있었다. (미로그인으로 `/orders`에 들어가도 화면은 빈 주문내역으로 그려질 뿐 오류로 죽지 않는다 — `OrderHistory`가 로그인 상태에서만 조회하기 때문이다.)

살아남는 고장, 즉 E2E가 놓칠 파손도 찾아봤다. 후보는 "초기 HTML의 로그인 상태"였다 — 서버가 그리는 첫 화면만 틀리고 자바스크립트가 뜬 뒤 고쳐지면, 하이드레이션 뒤를 보는 우리 단언은 못 잡을 수 있다. 그러나 이 앱은 로그인 여부를 서버가 한 번 정해 클라이언트가 그대로 쓴다(따로 다시 조회하지 않는다). 그래서 첫 화면과 하이드레이션 뒤가 항상 같아, 서버 쪽을 깨면 로그인한 뒤에도 로그아웃 상태로 남고 복원 테스트가 그걸 잡는다. 즉 "첫 화면만의 파손"이라는 게 이 앱엔 존재하지 않는다. (이 추론은 리팩토링에서 JavaScript를 끈 컨텍스트로 서버 HTML을 직접 단언해 증거로 바꿨다. 다만 "살아남는 고장이 없다"는 이 후보에 한한 말이었고, 다른 자리의 고장은 [§F](#f-리팩토링--초록불-아래에서-찾은-것)에 있다.)

**하나는 E2E만 잡을 수 있었다 — 실험 1.** `proxy`는 Next의 미들웨어다. "어느 경로를 로그인 검사에 걸지" 정한 목록(`matcher`)이 있고, 거기서 `/orders`를 빼면 그 경로는 검사 없이 통과된다. 이걸 왜 유닛 테스트로는 못 잡나 — 유닛 테스트는 `proxy` 함수를 직접 불러 "쿠키가 없으면 로그인으로 보내나"만 확인한다. 함수는 부르지만, "Next가 실제로 이 함수를 `/orders` 요청에 붙이나"라는 그 목록은 건너뛴다. 그래서 목록에서 `/orders`를 빼도 유닛 테스트는 모른다. 실제 브라우저로 `/orders`에 들어가 보는 E2E만 "로그인으로 안 튕기네"를 본다. (억지로 잡으려면 "목록에 `/orders`가 있나"를 그대로 확인하는 한 줄짜리 테스트를 쓸 수는 있다. 하지만 그건 코드를 베껴 같은지만 보는 것이라, 그 경로가 실제 요청에서 정말 지켜지는지는 하나도 증명하지 못한다. 그래서 통합이 잡는다고 치지 않는다.) 덧붙이면, 이 실험이 고장 낸 것은 가드의 판단 로직(쿠키가 있나 없나)이 아니라 "가드를 어느 경로에 걸지 정한 범위"다. 로직이 멀쩡해도 이 범위에서 빠지면 그 화면은 안 지켜진다 — 그래서 이 범위 설정도 인증 구현의 일부다.

**실험 1과 3은 같은 복원 테스트를 서로 다른 지점에서 실패시킨다.** 복원 테스트는 두 가지를 순서대로 본다 — 먼저 ⓐ 미로그인으로 `/orders`에 가면 로그인 화면으로 튕기나, 다음 ⓑ 로그인하면 원래 가려던 `/orders`로 돌아오나. 실험 1은 ⓐ에서, 실험 3은 ⓑ에서 실패시킨다. 여기서 중요한 건, 실험 1은 ⓐ에서 이미 멈춰 ⓑ까지 가지도 못한다는 점이다. 그러니 "ⓑ 확인이 진짜 일을 하나"는 실험 3으로만 알 수 있다 — 실험 1만으로는 ⓑ가 검증됐다고 말할 수 없다. 두 실험은 겹치는 게 아니라 각자 다른 지점을 지킨다.

**실험 2·3은 통합 테스트로도 잡혔다(vitest로 확인).** 그런데도 이 둘을 E2E에 남긴 이유는 이음새 때문이다. 유닛 테스트는 부품을 하나씩 떼어 본다 — 복원은 "redirect 값이 주어지면 그리로 보내나", 만료는 "401이 오면 로그인으로 보내나"를 확인하되, 그 값을 가짜로 넣어준다(목). 부품 각각은 맞는지 보지만, 그 값이 실제로 어디서 와서 어떻게 이어지는지는 안 본다. E2E만 그 이음새 전체를 훑는다 — `proxy`가 실제로 redirect 값을 심고 로그인 뒤 그 값으로 돌아오는 흐름, 서버가 세션을 읽어 401을 내고 로그인으로 보내는 흐름 전체를. C절에서 "인증을 E2E에 두는 건 조각이 아니라 이 전체 흐름 때문"이라 한 판단을 이 실험이 뒷받침한다.

**되돌림.** 실험마다 되돌린 뒤 `git diff`가 비어 있었고, 마지막에 E2E 전체가 통과했다. 고장 낸 코드는 하나도 남지 않았다.

## E. Advanced B — 에이전트 생성 검수

`npx playwright init-agents`로 planner→generator를 돌려, 인증 플로우(복원·만료·자격오류)를 테스트로 생성하게 했다. 생성기는 앱을 브라우저로 탐색하며 12개 테스트를 만들었다(그중 위조 쿠키용 `test.fixme` 하나는 뒤에서 걷어내, 커밋본은 11개다). 그걸 4단계에서 손으로 쓴 내 테스트와 비교한다.

생성기는 같은 목표를 받고 내 핵심 시나리오(복원·만료·자격오류)에 독립적으로 수렴했다. 그래서 검토할 값어치는 그 다음 — 생성기가 더 넣은 것과 사람이 걷어낼 노이즈 — 에 있다. 생성기가 잘한 것도 있다: 탐색만으로 우리 앱의 시나리오 쿠키(`scenario=expired`·`invalid`)를 찾아냈고, 포트 무관 `domain` 쿠키도 맞게 썼으며, 오픈 리다이렉트·계정 열거 같은 경계 상황을 더 봤고, 위조 서명 쿠키가 만드는 빈틈까지 짚었다.

**지운 것 — 세 묶음.**

1. **층이 틀린 것(네트워크 내부).** 로그인 응답이 200/401인지, 주문 응답이 401인지, 세션 쿠키가 httpOnly인지까지 본다. E2E는 사용자에게 보이는 결과(URL·에러 문구·헤더)를 봐야 한다. 상태 코드와 쿠키 속성은 API·유닛 테스트 몫이고, `toHaveURL`·`alert`가 이미 결과를 증명하는데 프로토콜에 결합만 더한다.
2. **한 상태를 여러 줄로 재확인.** 로그인 페이지에 닿을 때마다 이메일·비밀번호·버튼·링크가 보이는지 다섯 개씩 본다 — `toHaveURL("/login?redirect=%2Forders")` 하나면 충분하고, 나머지는 로그인 페이지 구조에 묶여 유지비만 는다. 로그인 뒤 상태는 로그아웃 버튼·"루퍼1"·헤더의 주문 내역 링크 셋이면 충분한데(로그인됨·맞는 유저·보호 경로 접근), 생성물은 거기에 `/orders` 페이지 제목(h1 "주문 내역")·(로그인 링크 없음)까지 더해 재확인한다.
3. **구현 결합.** `login()` 헬퍼가 `waitForResponse(/api/auth/login)`로 특정 API 주소에 묶인다. 그 응답 확인을 지우면 이 대기도 필요 없다 — 클릭 뒤 `toHaveURL` 폴링이면 충분하다.

**`test.fixme`를 지웠다.** 생성기가 위조 쿠키의 빈틈을 `test.fixme`로 남겨뒀는데, 과제가 비활성화 테스트를 금지하므로("하지 말 것"·공통 체크리스트) 걷어냈다. 발견 자체는 값지니 산문으로 남긴다 — 당시 `proxy`는 쿠키 존재만 보고 통과시켰고("`node:crypto`를 못 쓴다"는 근거는 뒤에 틀린 것으로 드러났다 — [§F](#f-리팩토링--초록불-아래에서-찾은-것)), 서버는 서명 불일치를 로그아웃으로 보는데 `useOrders`가 `enabled:false`라 401도 리다이렉트도 없이 로딩 문구에 멈췄다. 생성기가 짚은 이 빈틈은 리팩토링에서 proxy가 서명·TTL을 검증하게 바꿔 닫았고, 위조 쿠키는 `proxy.test.ts`의 한 갈래로 살아났다. AI는 "미구현이면 fixme로 남겨두자"는 흔한 관행을 그대로 뽑았고, 이 과제의 계약(활성 테스트만)엔 안 맞아 사람이 걷어내야 했다 — "AI가 뽑고 사람이 고른다"는 B의 요점이 여기서 그대로 드러난다.

**healer를 쓰지 않은 이유.** healer는 깨진 테스트를 AI가 자동으로 고쳐 다시 통과시킨다. 그러면 잡아야 할 회귀를 테스트가 스스로 덮어버려, 테스트가 계약이 아니라 앱이 바뀌면 따라 바뀌는 것이 된다. 실패는 사람이 "진짜 회귀냐 의도된 변경이냐"를 판단할 신호지 자동 재작성 대상이 아니다. "단언은 직접 정한다"는 이번 주 핵심과도 정면으로 어긋나 쓰지 않았다.

## F. 리팩토링 — 초록불 아래에서 찾은 것

PR 리뷰 뒤 인증·상태·테스트를 다시 훑고, 두 관점(인증 흐름 / 상태·캐시·테스트 유효성)의 적대적 점검을 돌렸다. 모든 테스트가 초록인 상태에서 결함이 열두 개 나왔다. §D의 "살아남은 고장 없음"은 **내가 고른 세 건에 한해** 참이었다 — 더 안 부숴서 못 찾은 것이지 없어서 못 찾은 게 아니었다.

### 찾은 결함과 고침

### 뒤집힌 판단

- **"proxy는 edge라 `node:crypto`를 못 쓴다"는 검증 없이 옮겨 적은 근거였다.** 스타터 파일 주석에서 물려받았는데, 그 주석은 출제 드라이런의 middleware.ts 시절 문장이고 이 레포엔 middleware.ts가 있었던 적이 없다. proxy는 Node 런타임이다. 존재만 보는 설계 자체는 정당했지만 그 근거는 처음부터 근거가 아니었고, 결함 1이 그 설계의 실제 대가였다.
- **"살아남은 고장 없음"은 고른 뮤테이션의 수에 갇힌 결론이었다.** 더 넓게 부수자 결함이 나왔다. 고른 3건은 "잡힐 걸 아는 것"이었다.
- **"로그아웃해도 브라우저 로컬 상태는 그대로"는 장바구니엔 맞고 사용자 귀속 서버 캐시엔 틀렸다.** 결함 4.
- **도구 제약(Stryker hang)을 이유로 rehydrate 테스트 범주를 없앤 것이 결함 5·6의 사각지대였다.** 변형 제외와 테스트 삭제는 다른 결정이다.

### 새로 더한 검증

JavaScript를 끈 컨텍스트로 서버 HTML의 로그인 상태를 양방향 단언(§D의 SSR 추론을 증거로), `request.get(…, {maxRedirects: 0})`으로 proxy의 307·Location을 브라우저 이동 없이 직접, 브라우저 저장소 기준 쿠키 속성(`httpOnly`·`sameSite`·`path` — `secure`는 로컬 HTTP라 제외), 실제 `ordersQueryOptions`·`useCreateOrder`로 `meta.auth` 배선(지우면 빨개짐), persist 실패 경로, 계측 예외, 언마운트 중 성공, 사용자 전환 캐시 격리. 고침마다 뮤테이션(해당 줄 제거 → 빨강)으로 테스트가 배선을 실제로 지키는지 확인했다.
