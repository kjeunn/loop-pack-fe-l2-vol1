# 8주차 테스트 전략 — 무엇을 어떻게 지킬지

## 0. 층을 나누는 기준

어느 항목을 단위·통합·E2E 중 무엇으로 검증할지는 감으로 정하지 않는다. 아래 세 기준으로 나누고, 15개 전부에 똑같이 적용한다.

- **단위와 통합을 가르는 기준.** 순수한 함수 호출만으로 — 함수의 반환값이나, 리듀서를 실행한 뒤의 스토어 값을 읽어서 — 확인되면 **단위**다. React를 렌더하거나 조회와 네트워크를 실제로 돌려야 결과가 드러나면 **통합**이다.
- **통합과 E2E를 가르는 기준.** jsdom이 흉내 내지 못하는 실제 브라우저 동작(뒤로가기 같은 history, 전체 새로고침, 화면을 넘나드는 실제 이동)이 있어야 확인되면 **E2E**다. 아니면 통합이다.
- **무엇을 검증하고 무엇을 믿고 넘길지.** 동작을 결정하는 판단·계산을 **우리가 직접 짰다면** 테스트로 확인한다. 라이브러리가 알아서 하는 부분(zustand의 저장·조회, React Query가 재시도 규칙을 적용하는 것, nuqs의 기본값 처리와 URL 변환)은 **믿고 다시 확인하지 않는다.**

한 가지 더. 테스트가 어떤 동작을 *거쳐 가는 것*과, 그 결과를 *검증하는 것*은 다르다. 통합·E2E는 React Query가 에러를 던지거나 nuqs가 URL을 만드는 과정을 거치지만, 실제로 검증하는 대상은 **우리가 짠 부분이 화면에 닿는 지점**뿐이다.

## 2. 층별 근거와 겹침 정리

**단위 (1·2·3).** 셋 다 함수 호출만으로 확인된다. 1은 우리가 짠 중복 제거·개수 계산을 확인한다(zustand의 저장은 믿고 넘긴다). 2는 조회 키가 올바른지만 보고, 그 키로 캐시가 실제로 어떻게 도는지는 통합이 본다. 3은 우리가 짠 걸러내기(`Number.isInteger && page>=1 ? page : null`)를 확인한다. 걸러진 뒤 null을 1로 바꾸는 건 nuqs 몫이라 여기서 다루지 않는다.

**통합 (4~12).** 조회 결과가 화면에 그려지는 공통 흐름은 4번이 대표로 확인한다. 5·6·7·8·9·10은 그 흐름을 다시 확인하지 않고 **각자 자기만 지키는 부분만** 검증한다 — 5는 빈 결과 갈래, 6은 에러 두 경우, 7은 재시도 복구, 8·9는 필터를 바꾸면 페이지가 1로 초기화되고 다른 필터는 유지되는 규칙, 10은 페이지를 옮겨도 필터가 유지되고 끝에서 버튼이 비활성인 규칙("목록이 바뀐다"는 4·11·2가 합쳐진 결과라 겉모습일 뿐이다), 11은 어느 컨트롤이 어느 URL 값에 연결됐는지, 12는 담기가 헤더 개수까지 이어지는지(여기엔 조회가 없고 렌더만 필요하다). **비동기 네 상태(로딩·성공·빈 결과·에러)는 4·5·6을 한 세트로 본다.** **6번은 한 항목을 두 테스트로 나눈다** — 4xx 인라인 경고와 5xx 에러 화면.

**E2E (13·14·15).** 셋 다 실제 브라우저 동작 위에서만 드러난다. 지키는 것이 서로 겹치지 않는다 — 13은 필터를 뒤로·앞으로 가기로, 14는 같은 필터를 새로고침으로(13은 새로고침 없이, 14는 뒤로가기 없이 서로 나눈다), 15는 장바구니를 화면 이동으로. nuqs와 React Query는 거쳐 가되, 검증은 브라우저만 할 수 있는 부분에만 건다. "새로고침해도 필터가 유지"는 두 층으로 나뉜다: 통합에서는 같은 URL로 다시 마운트해 복원되는지(11의 재진입), E2E에서는 진짜 새로고침 뒤에도 살아남는지(14).

### 2.5 통합에서 안 보는 것

- **픽셀·색·간격·위치·스크롤·줄바꿈·다크모드·반응형·z-index는 안 본다.** 이런 건 "제대로 보인다"를 `expect`로 쓸 수 없어, 사진을 찍어 비교하는 **시각적 회귀**의 몫이다. 그마저 "달라졌다"까지만 알려주지 "틀렸다"는 사람이 판정한다. (예: 긴 한글 상품명의 줄바꿈·말줄임, 폰트 폴백으로 밀린 레이아웃, z-index로 가려진 버튼.)
- 우리 통합 항목(4~12)은 요소의 존재·텍스트·속성·URL 상태만 확인하므로 jsdom에 레이아웃이 없어도 문제없다. 레이아웃이 필요한 드롭다운 위치·스크롤은 이미 별도 E2E(`select`·`dialog`)에 있다.
- **결제 성공 같은 전체 흐름도 안 본다.** E2E의 몫이다.
- 레이아웃이 필요한 통합이 늘면 Vitest Browser Mode(진짜 브라우저에서 통합 실행)를 고려한다. 느린 대신 레이아웃 문제가 사라진다. 지금은 그런 항목이 없어 jsdom으로 충분하다.

### 2.6 E2E에서 잡는 것과 안 잡는 것

- **13·14·15가 직접 확인하는 것:** 실제 브라우저에서만 나오는 기능 동작 — 뒤로·앞으로(history), 새로고침(reload), 화면 이동(cross-route). jsdom이 못 세우는 부분이라 여기 둔다.
- **프로덕션 빌드·실제 브라우저로 도니 곁들여 걸리는 것:** 라우팅·번들·실제 CSS 로드·폰트. 이것들이 깨지면 페이지가 안 떠 13·14·15가 빨간불이 된다(별도 항목 없이 스모크로 걸린다).
- **안 보는 것:** 화면이 보기 좋게 그려지는지(픽셀·레이아웃 — 시각적 회귀 몫) · 브라우저 차이(지금은 Chromium만; 필요하면 프로젝트 추가) · 로그인·결제·가입 같은 매출 경로(이 화면엔 없음).
- **왜 3개뿐인가:** E2E는 느리고 잘 깨져 아껴 쓴다. 15개 중 실제 브라우저가 꼭 필요한 셋만 올렸다.

## 3. 애매했던 판단 두 개

**(A) 5번을 단위로 볼까 통합으로 볼까.** 빈 결과는 "`products=[]`를 넘겨받은 화면이 잘 그려지나"로 읽으면 단위로 내려간다. 그런데 `ProductListResults`는 값을 넘겨받지 않고 **안에서 스스로 조회한다.** 빈 결과 화면에 닿는 유일한 길이 조회(MSW의 빈 배열)라서 **통합**으로 뒀다. 화면과 조회를 분리해 화면이 값을 넘겨받게 고쳤다면 빈·에러·성공 모두 단위로 내려갔을 것이다. 더 빠르고 깔끔하지만, "조회 결과가 빈 화면으로 이어지는 연결"은 못 잡는다. 이번엔 그 연결까지 지키려고 통합을 택했다.

**(B) 6번에서 5xx를 어디까지 볼까.** 인라인 4xx만 6번으로 두고 5xx는 "에러 화면으로 넘어가니 여기선 안 본다"고 밀어내면, `products/error.tsx`가 **실제로 뜨는지는 아무도 확인하지 않는 구멍**이 생긴다. 그래서 6번을 두 경우로 넓혔다 — 4xx 인라인, 5xx 에러 화면. 5xx를 단위(전파 규칙)로만 뒀다면 규칙의 *결정*은 잡아도 화면이 실제로 *뜨는지*는 비게 된다. `error.tsx`가 이미 있으니 그 렌더까지 통합으로 잡는 편이 정직하다.

## 4. 목록 밖

테스트는 유지비가 붙는다. 자동화는 반복을 싸게 만드는 것이라, 한 번만 볼 거면 손으로 보고, 같은 화면을 세 번째 여는 순간이 자동화 시점이다. 그래서 목록 밖은 "변경 빈도 × 실패 비용"으로 가른다.

- **다음에는 하면 좋겠다 — 위시리스트 담기·빼기 UI 상호작용.** 위시리스트 개수 파생은 1번이 단위로 잡지만, 담고 빼는 UI 상호작용(장바구니의 12번에 해당하는 위시리스트 짝)은 안 잡는다. 기능이 늘면 바뀔 수 있고(변경 빈도 중간), 틀리면 조용히 UX가 나빠진다(실패 비용 중간). 장바구니와 짝이라 그다음 순위다.
- **앞으로도 안 하겠다 — 스켈레톤 카드 개수·픽셀 배치.** 디자인 따라 자주 바뀌고(변경 빈도 높음), 틀려도 기능은 멀쩡하다(실패 비용 낮음). 자주 바뀌는데 값어치는 낮아, 테스트가 유지 부담만 남긴다.

## 부록 A. 정책 확인용 단위 테스트 (15개 밖, 6·7이 기대는 규칙)

| 대상           | 확인 내용                                                                      | 방법                                                                           |
| -------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 재시도 규칙    | 네트워크 실패는 한 번 재시도, 그 뒤엔 안 함, 네트워크 아닌 실패는 재시도 안 함 | `getDefaultOptions().queries.retry`로 함수를 꺼내 직접 호출 (또는 함수로 분리) |
| 에러 전파 규칙 | 5xx이고 데이터가 없으면 던지고, 4xx는 안 던짐                                  | `getDefaultOptions().queries.throwOnError` 직접 호출 (또는 분리)               |

테스트용 QueryClient는 재시도를 꺼서(`retry:false`) 결과를 일정하게 만든다. 자동 재시도는 그때만 켜서 보는 게 아니라, 위 규칙 함수를 단위로 직접 확인한다.

## 부록 B. 믿고 넘기는(다시 확인 안 하는) 바깥 계약

- **route.test.ts (node 환경):** 9번의 정렬 순서 정확성(전체 순서를 `toEqual`로 고정), 시나리오 응답. 프론트는 믿고 참조만 한다.

## 5. 먼저 해둘 일 (0단계)

**환경**

- `msw` 설치, MSW 서버를 켜고 끈다(`onUnhandledRequest:"error"`). 기본은 성공 응답만 두고, 실패·지연·빈 결과는 그 테스트 안에서 덮는다. `/api/products` 외에 새는 요청이 없는지 확인한다.
- `fetch`를 직접 바꿔치기하던 4개 파일을 MSW로 옮긴다: `page.test.tsx` · `queries.test.ts` · `ProductListResults.test.tsx` · `ProductListView.test.tsx`.
- DOM이 필요한 테스트와 아닌 테스트를 나눠 돌린다(전부 DOM으로 돌리지 않는다). 환경 준비 시간을 전부 DOM일 때와 비교해 기록한다.
- Playwright를 `pnpm dev` 대신 프로덕션 빌드 위에서 돌게 바꾸고, E2E를 어느 명령에 넣을지 정한다.
- `parseAsPage`를 export한다(3번에서 `parse()`만 따로 확인하려면 필요).

**격리와 일관성 (꼭 필요)**

- **매 테스트 뒤 zustand 스토어(`cart`·`wishlist`)를 초기화하고 `localStorage`를 비운다.** 스토어가 모듈 단위로 하나뿐이라, 안 하면 1·12·15가 서로 오염된다.
- 테스트용 QueryClient는 `retry:false`.

**작성 규칙 (2단계)**

- 이름은 **조건 + 행동 + 결과**로 쓴다. `works`·`renders`·`should be true` 금지. 실패 리포트에서 이름만 읽고 원인이 짐작돼야 한다. (예: "재고가 0이면 담기 버튼이 잠긴다")
- **공개 동작만 단언한다.** `validate()가 불렸다`·`isLoading이 true다`·`setFilter가 한 번 불렸다`·렌더 횟수 같은 내부는 보지 않는다 — 통과해도 보장이 없고 리팩토링 때만 깨진다. 대신 사용자가 보는 결과("필터를 바꾸면 목록이 바뀐다")를 단언한다.
- **`toBeVisible()`에 기대지 않는다.** jsdom엔 레이아웃이 없고 CSS 모듈 스타일도 적용되지 않아, `toBeVisible()`는 CSS 클래스로 숨긴 것·가려짐·잘림·화면 밖을 못 잡는다(가려진 버튼도 통과한다). 조회는 존재·텍스트·역할·속성(`toBeDisabled` 등)으로 한다. "보이나 안 보이나"는 시각적 회귀 몫.
- `keepPreviousData` 때문에 필터를 바꿔도 이전 목록이 남는다(스켈레톤을 다시 안 띄운다). 그래서 전이는 "이전 목록 → 새 목록"으로 확인한다.
- `waitFor`는 첫 비동기 대기에만 쓰고, 나머지는 동기로 확인한다.
- `skipHydration` 때문에 스토어를 그리는 테스트는 하이드레이션 상태(`useCartHydrated`)를 고려한다.

## 6. mock이 현실과 어긋나는 걸 줄이는 법

모킹한 부분은 "검증하지 않기로 한 부분"이다. 서버가 응답을 바꿔도(예: `totalCount`→`total`) 핸들러가 옛날 그대로면 테스트는 초록불인데 프로덕션만 깨진다. 없앨 순 없고 줄인다.

- **MSW 핸들러·픽스처에 실제 응답 타입(`ProductListResponse`)을 붙인다.** 서버 스키마가 바뀌면 타입 에러로 먼저 걸린다.
- **픽스처는 팩토리 하나에서 만든다.** 테스트마다 객체 리터럴을 새로 쓰지 않는다 — 고칠 곳이 한 곳이 된다.
- **실제 응답을 주기적으로 통과시킨다.** 우리 E2E는 프로덕션 빌드의 실제 `/api/products`를 타고, `route.test.ts`(node)가 실제 응답 스키마를 고정한다 — 이 둘이 mock만으로는 못 잡는 어긋남의 안전망이다.
